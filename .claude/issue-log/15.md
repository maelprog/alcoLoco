# Journal — #15 API historique des consommations d'un profil

Rien n'a commencé sur cette issue. Ce fichier porte des dettes identifiées ailleurs.

## Dette léguée par #3 (vérification 1 de la PR #45, 2026-08-20)

#3 pose le contrat de pagination par curseur mais n'a **aucune collection métier à paginer** : les
types existent, ne sont enregistrés dans aucun document OpenAPI, et trois écarts n'ont donc aucun
effet aujourd'hui. **#15 est la première à les rendre visibles** — c'est elle qui les ferme.

1. **`limit` sera publié en `string`.** `crates/api/src/pagination.rs:33-38` type `limit: Option<String>`
   (choix défendable côté validation, documenté sur place). `IntoParams` produit alors
   `{"name":"limit","schema":{"type":"string"}}` : ni entier, ni `minimum`/`maximum`, ni `default` —
   `DEFAULT_LIMIT` (50) et `MAX_LIMIT` (200) **n'atteignent jamais le document**. La description reprend
   en outre le lien rustdoc brut (``« at most [`MAX_LIMIT`] »``).
2. **`next_cursor` n'est pas `required` dans le schéma de `Page<T>`.** Le contrat veut le membre
   **toujours présent** (`{ "items": [...], "next_cursor": <string|null> }`) et le fil est conforme,
   mais le schéma généré donne `"required":["items"]` seulement, `next_cursor` étant `Option<String>`.
   Contrat publié ≠ contrat réel.
3. **`PageRequest` a des champs `pub` et aucun invariant.** `PageRequest { limit: 0 }` +
   `Page::from_rows(vec![1,2,3], …)` rend `items: []`, `next_cursor: None` — soit « collection
   épuisée » alors qu'il reste des lignes. Inatteignable depuis une query string (validée `1..=200`),
   **atteignable par un handler** — donc par #15.

⚠ Vérifier aussi, en enregistrant les types dans le document, que le piège `utoipa` légué par #3
s'applique : `utoipa` ne voit **pas** à travers un alias de type pour les horodatages, et sa feature
`chrono` ne lève pas la contrainte (reproduit par le vérificateur de #3). Tout champ de date exige
un `#[schema(value_type = String, format = DateTime)]` écrit à la main. Cf. `crates/api/src/timestamp.rs`.

## Dette léguée par #4 (vérification de la PR #46, 2026-08-21)

**M1 — les bornes de pagination du front peuvent dériver du backend en silence.**
`web/src/app/core/api/page.ts:12,15` recopie `DEFAULT_PAGE_LIMIT = 50` et `MAX_PAGE_LIMIT = 200` de
`crates/api/src/pagination.rs:20,23`. Le commentaire dit « mirrored from », mais **rien ne le tient** :
mutation mesurée par le vérificateur (`999` / `500`) → `npm run lint` vert et **46/46 vert**. Un
`MAX_PAGE_LIMIT` monté à 500 laisserait le front envoyer `limit=500`, que l'API rejette en 400 —
panne ni impossible par construction, ni visible.

C'est le pendant front du piège « un doc-comment n'est lié à aucune constante » du briefing.

Accessoirement : **`DEFAULT_PAGE_LIMIT` n'est référencé nulle part** dans `web/src` — constante morte,
donc muette par construction, tant qu'aucun écran ne pagine.

**#15 est la première issue à consommer une collection paginée** (sauf si #8 pagine `GET /profiles`,
auquel cas elle passe devant) : c'est elle qui ferme ce trou, par un test qui **lit la source
backend** plutôt que de recopier ses valeurs.
